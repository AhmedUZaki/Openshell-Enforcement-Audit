Experiment: per-endpoint and per-METHOD network enforcement, observed live.
Three questions, one disposable sandbox:
  1. An endpoint that IS in the policy: does a GET work?
  2. An endpoint that is NOT in the policy: can a request get a 200?
  3. A rule that allows only GET: does OpenShell block a POST to the same
     endpoint?
Run on 2026-11-19 against a real OpenShell gateway/sandbox, no agent involved.
Every value below is a REAL observed result, never a predicted one filled in
by hand. Recorded with the allow-listed fields from baseline/README.md.

OpenShell version: 0.0.116
Sandbox: 'oea-net-test', created fresh for this run from the 'restricted' tier
(deny-by-default network, see policies/restricted.yaml) and deleted at the end.
All stages ran in that ONE sandbox/container; only the policy was changed
between stages (versions and hashes below).
Setup, outside what was measured: curl installed in the container as root with
`docker exec -u root ... apt-get install curl` (runs outside the OpenShell
supervisor). Before the sandbox existed, all three requests below returned 200
from the WSL host with no OpenShell involved, so a block cannot be blamed on a
site being down.

Command actually run for every request (inside the sandbox, as the sandbox
user, through OpenShell):
  openshell sandbox exec -n oea-net-test -- sh -c '
    code=$(curl -s -m 20 -o /tmp/oea-b -w "%{http_code}" "$@"); rc=$?;
    echo "HTTP_STATUS:$code CURL_EXIT:$rc";
    if [ "$code" != 200 ]; then head -c 300 /tmp/oea-b; echo; fi;
    rm -f /tmp/oea-b' _ <curl arguments shown per request>
The response body is printed only when the status is not 200. A 200 body from
httpbin echoes the client's IP address, so it was never captured; a non-200
body here is OpenShell's own.

The GET-only rule (explicit, not the 'read-only' preset: --dry-run shows that
preset only as an opaque `access: read-only` flag, so it does not say which
methods it allows; an explicit rule is literally "GET only"):
  openshell policy update oea-net-test \
    --rule-name net-test-get \
    --binary /usr/bin/curl \
    --add-endpoint httpbin.org:443::rest:enforce \
    --add-allow 'httpbin.org:443:GET:/**' \
    --wait
which expands to
  endpoints: host httpbin.org, port 443, protocol rest, enforcement enforce,
  rules: allow method GET, path /**; binaries: /usr/bin/curl

What this shows
- An endpoint outside the policy cannot return a 200: the connection itself is
  refused (curl exit 56, status 000), and the log names the reason.
- With only GET allowed, the connection to the endpoint opens (NET:OPEN
  ALLOWED) but the POST is stopped at the HTTP layer (engine:l7), returning
  403 with an OpenShell JSON body, before it reaches httpbin.
- The block is caused by the rule, not by the server: the same POST returns
  200 once a POST rule exists, and a POST to a different path stays blocked.
- Evidence for each request is OpenShell's own decision line (naming the rule
  and the layer) plus the policy version/hash, not the HTTP status alone.

Limits of this experiment (not tested, not assumed)
- Only POST was tried against the GET-only rule, not PUT/DELETE/PATCH, and
  not HEAD (baseline_test3 showed HEAD allowed under the 'read-only' preset).
- What the 'read-only' preset itself allows was not tested here.
- Rules are tied to /usr/bin/curl; another binary reaching the same endpoint
  was not tried. Plain HTTP (non-TLS) and --add-deny rules were not tried.
- One sandbox/container throughout, so time and the sandbox's history (Stage 0
  was a denied first attempt) were not controlled. Each request was run twice
  with identical results.
- The log capture window overlapped by up to a second, so neighbouring
  requests' lines sometimes appeared together; the lines above are those that
  belong to each request, by method, host and path.
